# 停车场与车道

> 所属：HCP > 停车场 > 停车场管理（停车场 / 出入口 / 车道 / 岗亭 / 对讲柱 / 显示屏）
> 版本演进与具体需求见 `版本迭代/`；本文只讲**不随版本变的业务概念**。

---

## 一句话定位
停车场的"物理骨架"——把现实里的车场、出入口、车道、闸机、抓拍机组织成平台里可管可控的结构。放行、收费、诱导都长在这套骨架上。

---

## 核心概念一：四级物理层级
```
停车场 ─┬─ 出入口 ─┬─ 车道（入口/出口）─── 关联设备（抓拍/道闸/刷卡/显示屏/对讲）
        │          └─ 车道 …
        └─ 出入口 …
```
- **停车场**：计费、放行、车位的归属主体，可有**子停车库（子库）**。
- **出入口**：一组进出通道的集合。
- **车道**：真正控制一次通行的最小单位，分**入口道/出口道**，挂着抓拍与道闸设备。
- 一辆车的一次通行 = 走某条**车道** → 被车道上的设备识别 → 按规则控道闸。

**子库（子停车库）是一层特殊的从属结构**（源自 2.4 基线）：主库下可挂多个子库，但**子库不能再嵌套二级子库**；子库**只支持配包期规则**（收费规则等仍归主库）；放行上**任一子库车道放行则主库也放行**；计费上**进出子库停留时间不计费，只算主库停留时段**。

**主库与子库的权限可分开授权。** 一个账号可以只有子库权限而无主库权限：此时主库信息置灰并提示"暂无该停车场权限"，但可直接进入并管理其子库，主库的出入口也不展示。业务背景是多物业/分租场景——整个综合体为一个主库，各租户只管理各自的子库。

> 层级是业务上的从属关系，权限是管理上的切分，两者不必对齐。"主库置灰、子库可进入"是正常形态，非异常。

## 核心概念二：车道是"设备 + 规则"的绑定点
车道之所以是核心，因为它把两件事绑在一起：
- **设备**：抓拍单元（认车牌）、出入口控制设备/道闸（抬杆）、刷卡对讲（认卡认人）、显示屏（给车主看）。其中必须有一个被指定为**道闸控制单元**，否则抬不了杆。
- **规则**：这条道走什么车（可限定车型、设摩托车专用道）、用什么放行判断方式（继承停车场或自定义）。

> 心智模型：**停车场定政策，车道落地执行**——设备接在车道、规则最终在车道生效。

## 核心概念三：出入口设备各司其职
一条车道上的设备是一条"识别→决策→反馈"流水线：
- **抓拍单元 / ANPR**：读车牌，是自动放行的眼睛。
- **刷卡 / 对讲设备（含对讲柱）**：认卡认人、异常时呼叫岗亭。
- **出入口控制设备（道闸）**：执行抬杆，是手。
- **显示屏 / 音频**：给车主反馈车位、金额、放行结果，是嘴。

理解要点：放行判断方式选什么，取决于车道配了哪些"眼睛"——没有刷卡/对讲就不能选"人脸·卡片优先"。

出入口控制设备细分**卡箱 / 票箱**：卡箱做刷卡/吐卡/还卡，票箱做取票/扫票——对应两类临时车放行方式（票箱取卡还卡、或岗亭刷卡发卡）。一条车道最多两个抓拍机（配"匹配时间"避免单次过车重复记录，取车牌置信度高者），一个出入口控制设备、**最多两个刷卡对讲设备**（一卡通场景需要两台分别刷卡开门）、一个显示屏；抓拍机/出入口控制/刷卡对讲都可被指定为道闸控制单元。

**道闸控制单元由哪个设备担任，决定了该车道的能力范围**：只有当道闸控制单元是**抓拍单元**时，该车道才能配置「离线放行」——离线时只有抓拍机能自行识别车牌、比对下发的名单并控制道闸（见 `放行规则.md`）。由卡箱/票箱控闸的车道，断网后无法自主放行。

车道除关联设备外还可**关联监控点（视频画面）**，用于过车时提供更多车辆信息（数量有上限）。它不参与放行判断，仅作辅助查看。

## 核心概念四：出入口显示屏按车辆分类分别配置
车道上的 LCD/LED 显示屏不使用统一文案，而是**按车辆分类（全部 / 固定车 / 临时车 / 访客车 / 各车辆名单）分别配置**，且区分两种时机：
- **过车显示**：有车经过时显示什么（车牌号码、入场时间、空余车位、名单空余车位、到期提醒、车辆类型、未放行提示，收费场另有收费金额、账户余额）。
- **空闲显示**：无车时显示什么（欢迎语、空余车位）。

> 屏上可插入的字段受停车场收费模式约束：收费金额、账户余额只在收费场存在，可据此判断现场是收费场还是免费场。

## 边界与异常

| 场景 | 系统行为 | 出处 |
|---|---|---|
| 一条车道关联设备的数量上限 | 抓拍机 ≤2（配"匹配时间"避免单次过车重复记录，取置信度高者）、出入口控制设备 1 个、**刷卡对讲 ≤2**（超选只取前两个）、显示屏 1 个、联动监控点 ≤3 | v2.5 / v3.0 / v3.1.1 |
| 勾选「摩托车专用车道」 | 与「禁止通过的车辆类型」互斥，勾选后后者禁用 | v3.2 |
| 账号只有子库权限、无主库权限 | 主库信息置灰 + 提示「暂无该停车场权限」，主库出入口不展示；子库可正常进入管理。**这是正常形态，非异常** | v2.5 |
| 子库的能力边界 | 不能再嵌套二级子库；**只支持配包期规则**（其余收费规则归主库）；进出子库停留时间不计费 | v2.4 基线 |
| 车道未指定道闸控制单元 | 无法抬杆放行 | v2.4 基线 |
| 道闸控制单元是卡箱/票箱 | 该车道无法配置离线放行（断网后不能自主认牌决策） | v2.5 |
| 免费场配置出入口显示屏 | 「收费金额」「账户余额」字段不出现，只有名单空余车位 / 空余车位 | v3.0 |

## FAQ
- **车道为什么要指定"道闸控制单元"？** 车道上可能挂多个设备，得明确哪个负责抬杆，否则无法放行。
- **摩托车专用道是什么？** 把某条车道限定只走摩托车，与"禁止通过的车辆类型"互斥。
- **停车场级和车道级设备/规则的关系？** 停车场是归属与默认策略，设备实际挂在车道、规则最终在车道兑现。车道默认"继承所属停车场规则"，关掉才可自定义。
- **为什么这条车道配不了离线放行？** 它的道闸控制单元不是抓拍单元。断网时只有抓拍机能独立完成"认牌→比对名单→抬杆"。
- **关联监控点和关联抓拍机有什么区别？** 抓拍机参与识别与放行判断；关联监控点只提供视频画面作为辅助信息，不参与判断。
- **只有子停车场权限的账号能干什么？** 能正常管理自己的子库；主库信息置灰提示"暂无该停车场权限"，主库出入口也不展示。这是多物业/分租场景的正常形态。
