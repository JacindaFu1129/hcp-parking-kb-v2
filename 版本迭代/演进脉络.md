## 一、车辆有效期 → 停车通行有效期

**为什么会有这条线**：有效期在不同版本承担的角色一直在变。v3.2 的分叉处理（有的客户删、有的客户留）只有回看 v2.5 才讲得通。

| 阶段 | 有效期当时是什么角色 |
|---|---|
| **v2.5** | 「名单下发」把名单**连同有效期**推到设备。在纯 ANPR 客户那里，这个下发的有效期成了**设备侧的实际判据** |
| **v3.0** | 「车主 ID」等字段补齐，车辆有效期作为车辆表单的一级字段存在 |
| **v3.1 / v3.1.1** | 停车场侧改由**停车场通行权限**与**充值管理**承载有效期；车辆有效期字段仍在，但对停车场放行**实际不生效** |
| **v3.2** | 收敛为唯一来源。**新装平台**隐藏车辆有效期；**旧版升级且仅有 ANPR License** 的客户保留 |

**留下了什么包袱**
1. **新装与升级两套行为并存**，同一个字段在不同客户现场可见性不同，问"车辆有效期在哪"没有统一答案。
2. **平台侧生效的有效期与下发到设备的有效期未必一致**。一辆车既属名单又有通行凭证时，下发给设备只能是一个值，差异只在离线或纯 ANPR 场景暴露。
3. **名单有效期未配置时的语义至今未定**（永久有效 or 回退）——见 `../待确认.md`。

**怎么用这条线**
讨论任何有效期问题前，先确认三件事：**装了哪些 License**（有无停车场/出入口）、**新装还是升级**、**有没有在用名单下发**。三个答案不同，同一个问题的结论完全不同。

> 逐条改动见 `v2.5.md`、`v3.2.md`；概念定义见 `../业务认知/术语与实体.md` 第二节。

## 二、放行判断方式：从"或"到"与"

**为什么会有这条线**：这是一次**主动收窄**——引入时给了三个选项，一个版本后砍掉一个，且砍掉的正是默认项。

| 阶段 | 变化 |
|---|---|
| **v3.0** | 引入「放行判断方式」，三选项，**默认「单项条件认证」**：人脸/刷卡/ANPR **任一**通过即放行（"或"逻辑） |
| **v3.1.1** | **删去「单项条件认证」**，只留 ANPR 抓拍优先 / 人脸·卡片优先（均为"与"逻辑），默认 ANPR |

**为什么砍**："或"逻辑使整体安全水位取决于**最弱的那一路识别**——只要任一路能过，防顶包、防跟车的校验就形同虚设。留下的两个选项都是"与"，差别只在**先验哪一路**。

**留下了什么包袱**
- v3.0 期间的现场可能仍在用"或"的心智描述这个功能，沟通时需确认版本。
- 判断方式决定的**不是使用哪个设备**，而是**是否要求双重认证及验证顺序**——这一点长期被误解。

**怎么用这条线**
再有人提"任一条件通过即可放行"的需求时，先讲这段历史：它被评估过、上线过、又被删掉了，原因是安全水位问题。

> 逐条改动见 `v3.0.md`、`v3.1.1.md`；概念见 `../业务认知/放行规则.md` 概念一。

## 三、名单下发：一个动作，两条链路，一个"丐版出入口控制"

**为什么会有这条线**：这是**整个停车场知识库里最容易出错的地方**——同一个「名单下发」开关，在两种 License 下做的是两件完全不同的事。

| 阶段 | 变化 |
|---|---|
| **v2.5** | 同时上线两条分支：**只有 ANPR** → 下发到**相机**，产生黑白名单**报警**；**有出入口** → 下发到**车道**，实现**离线放行** |
| **v2.5 起持续** | 部分无停车场 License 的客户，用「ANPR + 名单下发 + 报警输出联动道闸」自建了简易出入口控制 |
| **v3.2** | 有效期整合时必须为这批客户**留后门**，否则直接改变他们现场的开闸行为 |

**留下了什么包袱**
- 这是一条**被实际使用但从未被正式定义**的产品用法。它不在任何功能清单里，却限制了后续所有涉及名单、有效期的改动。
- 「下发成功」≠「配置生效」，排查"离线放行不起作用"时首先要区分走的是哪条链路。
- 离线放行**只对名单车生效**（临时车、访客车在设备侧无名录可比对），且**仅限道闸控制单元 = 抓拍单元**的车道。

**怎么用这条线**
凡涉及名单、名单有效期、名单下发的需求，评审时必问一句：**"这对只有 ANPR 的客户有什么影响？"**

> 逐条改动见 `v2.5.md`；概念见 `../业务认知/车辆与名单.md` 概念六、`../业务认知/放行规则.md` 概念六。

## 四、停车场权限：从"授权"到"售卖"

**为什么会有这条线**：同一个「停车场通行」入口，在两类停车场下的性质被逐步区分开。

| 阶段 | 变化 |
|---|---|
| **v3.0** | 停车场选择改资源树，父子库可展开——权限仍在人员/车辆详情里配 |
| **v3.1** | 免费场的通行权限逻辑理顺（控制通行车辆数、名单车不可反勾选） |
| **v3.1.1** | **收费场下不再支持在人员/车辆详情配置停车场权限**，一律回到充值管理；详情页降为只读 + 跳转 |

**沉淀出的心智模型**：**免费场"授权"，收费场"售卖"。** 同一个入口，在免费场是配置项，在收费场变成只读凭证。

**留下了什么包袱**
- 用户仍会在收费场的车辆详情里找"改权限"的入口，找不到——这是**设计意图**，不是缺陷，但提示引导是否到位值得复看。
- 收费场的有效期因此变成"充值的副产物"，与包期分段、断档强绑定。

> 逐条改动见 `v3.0.md`、`v3.1.md`、`v3.1.1.md`；概念见 `../业务认知/车辆与名单.md` 概念三。

## 五、屏显与余位口径的长期收敛

**为什么会有这条线**："屏上的数字和实际对不上"是反复出现的现场问题，历版都在打补丁。

| 阶段 | 变化 |
|---|---|
| **v2.5** | 屏类型**三分类归一**（入口显示屏 / 入口引导屏 / 停车诱导屏）；余位支持**跨停车场**合并统计 |
| **v3.0** | 新增「固定车位是否计入空余车位计算」；室外引导屏支持余位为 0 时显示 0/X/FULL |
| **v3.1.1** | 各类屏「空余车位为 0 时显示」**统一**为 0/X/FULL/自定义 |
| **v3.2** | 矢量地图分区颜色，进一步做可视化辨识 |

**留下了什么包袱**
判断一块屏上的数字，至今需要确认**三件事**：统计哪几个停车场、是否含固定车位、余位为 0 时怎么显示。这三个开关分散在不同页面，没有一处能一眼看全。**这是一个明确的体验缺口**，见 `../设计视角/体验缺口.md`。

另外，整层余位与方向余位可能**来自不同设备**（ANPR 过车统计 vs 车位相机逐位统计），算法不同，对不上是正常的。

> 逐条改动见 `v2.5.md`、`v3.0.md`、`v3.1.1.md`；概念见 `../业务认知/车位诱导与寻车.md` 概念五。

## 六、中东 SIRA 本地化：从定制到基线

**为什么会有这条线**：一次本地化需求**从数据模型层改变了"车牌"这个实体**，因此影响面持续扩散了三个版本。

| 阶段 | 变化 |
|---|---|
| **v2.5** | 阿联酋定制**转基线**：新增「车辆属性设置」菜单（车辆类型/自定义属性/区域设置）；启用中东北非后国家/地区转为车牌小字 |
| **v3.1（CS）** | SIRA 车牌特殊字段支持——监控页面 |
| **v3.2** | 中东 SIRA 优化：多字段车牌贯穿泊车记录/剩余车辆检索/车位监控/导出/详情 |

**留下了什么包袱**
- **车牌不是一个字段**，而是 `国家/地区 + 小字 + 号码 + 大小 + 类型 + 颜色` 的组合。任何新增的车牌相关页面都要考虑它。
- ⚠ **国家/地区、车牌区域、Category 三者彼此独立、不可互相推导**——这条约束反复被误解。
- 按车牌搜索需**分段输入**，与通用场景的单输入框交互不同。

**怎么用这条线**
设计任何涉及车牌展示或检索的新页面时，先问：**这个页面在中东北非区域设置下长什么样？**

> 逐条改动见 `v2.5.md`、`v3.1.md`、`v3.2.md`；概念见 `../业务认知/监控报表与运维.md` 概念三。
