# 角色与旅程

> ⚠ **本文证据等级混合**：角色划分与任务链路由既有文档与实况截图支撑；**「卡点」一列多为推断**，未经用户研究验证，作方案时按提议而非事实使用。

---

## 一、角色

| 角色 | 在哪个端 | 关心什么 | 典型任务 |
|---|---|---|---|
| **实施 / 配置工程师** | BS | 一次性把现场搭起来、别漏配 | 建停车场 → 配出入口车道 → 关联设备 → 配规则 → 配诱导 |
| **物业管理员** | BS | 日常运营、权限发放、看经营数据 | 加车加人、发包期、查记录、看报表 |
| **租户 / 子库管理方** | BS | 只管自己那一块 | 仅有子库权限，管自己的子停车库 |
| **岗亭值守员** | **CS** | 当班别出错、交班账要清 | 处理异常放行、出场收费、交班 |
| **中心收费员** | CS | 先收后放，提高通行效率 | 中心收费、减免、打小票 |
| **运维人员** | BS | 设备在线、钱箱别满 | 巡检、看异常、缴费机钱箱 |
| **车主** | 现场硬件 | 快点进、找到位、快点出 | 过闸、看屏、寻车终端找车 |

> 关键分工：**BS 是配置侧，CS 是值守侧。** 同一业务在两端各有一套界面——做设计前先确定给谁用。

## 二、旅程 A：把一个停车场搭起来（实施工程师 · BS）

这是**配置链路**，一次性但最重、最容易漏。

```
建停车场 ──→ 定收费模式 ──→ 建出入口 ──→ 建车道 ──→ 关联设备 ──→ 指定道闸控制单元
   │              ↑ ★总开关            │
   │                                    └──→ 配车道规则（继承 or 自定义）
   ├──→ 配放行规则（按五种身份分别配）
   ├──→ 配收费规则（仅收费场）
   └──→ 配停车诱导（按楼层四步向导：关联设备→配置地图→配置车位类型→标记设备）
```

**已知卡点**

| 卡点 | 依据 |
|---|---|
| **收费模式必须最先定**——它级联决定后面一半菜单存不存在，改起来代价大 | ✅ 已确认（`业务认知/00_总览.md`） |
| **道闸控制单元由谁担任，决定这条道能不能配离线放行**，配到后面才发现开关是灰的 | ✅ 已确认（v2.5） |
| 车道规则的"继承 / 自定义"是隐性分叉，不展开看不出这条道和别的道有什么不同 | 🔶 推断 |
| 诱导四步向导必须用**矢量地图**才能标车位，用了静态图要推倒重来 | ✅ 已确认 |
| 设备能力不足时靠**置灰 + 提示**告知，但看不到"该换什么设备才能用" | 🔶 推断 |

## 三、旅程 B：日常运营（物业管理员 · BS）

```
加车 / 加人 ──→ 配停车场通行权限 ──→ 到期提醒 ──→ 续费 or 失效
                    │
                    ├─ 免费场：在人员/车辆详情里【授权】
                    └─ 收费场：去充值管理【售卖】（详情页只读）
```

**已知卡点**

| 卡点 | 依据 |
|---|---|
| **收费场找不到改权限的入口**——详情页只读，需跳转充值管理。这是设计意图，但引导是否够强待验证 | ✅ 机制已确认 / 🔶 卡点为推断 |
| **四种"有效期"名字接近，实际控制的东西不同**，选错字段等于白配 | ✅ 已确认，见 `业务认知/术语与实体.md` |
| 一车多场多段包期，列表压缩展示时**断档容易被忽略** | ✅ 已确认（v2.5） |
| **批量充值是覆盖式的**，与单车"续费"语义相反，误用会清掉原有效期 | ✅ 已确认（v2.5） |

## 四、旅程 C：岗亭一个班次（值守员 · CS）

```
登录进车辆监控页 = 上班
   ↓
处理异常：无牌车 / 识别错 / 呼叫中心 / 登记放行（记备注、占名单车位）
   ↓
出场收费：自动算费 → 减免 / 改车型 / 车牌矫正重算 → 现金 or 账户扣款 → 抬杆
   ↓
随时看【收费概览】：总额 / 账户扣除 / 现金 / 减免
   ↓
交班 or 结束工作（二次确认）→ 手动下班才产生班次记录
```

**已知卡点**

| 卡点 | 依据 |
|---|---|
| **只有手动下班才产生班次记录**——直接关客户端等于这个班的账没了 | ✅ 已确认（v3.1.1 二次确认即为此而加） |
| 原先金额只能在交班弹框里看，故独立出「收费概览」 | ✅ 已确认（v3.1.1） |
| 看远端站点时本地专属操作被隐藏，**按钮消失的原因不直观** | ✅ 机制已确认 / 🔶 卡点为推断 |
| 计费不透明——多规则叠加时需展开明细才看得懂 | ✅ 已确认（v3.1.1 为此做了明细悬浮） |

## 五、旅程 D：车主一次进出（现场硬件）

```
入口：抓拍识别 → 判断身份 → 屏上给反馈 → 抬杆
   ↓
场内：入口引导屏看整场余位 → 停车诱导屏看分方向余位 → 车位屏红绿灯
   ↓
（离场前）中心 / 缴费机先付 或 出场岗亭付
   ↓
找不到车 → 自助查询设备（寻车终端）输车牌反查
   ↓
出口：算账 → 放行
```

**已知卡点**

| 卡点 | 依据 |
|---|---|
| **屏上余位数与实际空位对不上**——取决于三个分散的开关（统计哪几个场 / 含不含固定车位 / 余位为0怎么显示） | ✅ 已确认，见 `版本迭代/演进脉络.md` 主线五 |
| 整层余位与方向余位**来自不同设备、算法不同**，天然可能不一致 | ✅ 已确认 |
| 识别错了只能靠**呼叫中心**兜底（合并记录、生命周期约 3 分钟） | ✅ 已确认 |
| 寻车终端面向公众且落地海外，**多语种车牌输入**是硬需求 | ✅ 已确认（v3.2 自定义键盘） |
